# 보안 사고 대응 런북

이 문서는 공격 의심 상황(계정 오남용, 대량 요청, 의심 트래픽, 취약점 경고) 발생 시 즉시 대응하기 위한 절차입니다.

## 0) 트리거 조건

아래 중 하나라도 발생하면 보안 사고 대응을 시작합니다.

- GitHub Actions `Security`/`CodeQL` 실패
- Dependabot PR에 high/critical 경고
- Supabase 로그에서 비정상 요청 급증
- 사용자 제보(권한 없는 데이터 접근, 비정상 데이터 변경)

## 1) 초기 분류 (10분 이내)

- 영향 범위 확인: 읽기/쓰기/삭제 중 무엇이 가능한지
- 공격 대상 확인: 특정 테이블인지, 전체 서비스인지
- 재현 여부 확인: 같은 요청이 반복되는지
- 심각도 분류:
  - `SEV-1`: 데이터 유출/파괴 가능성
  - `SEV-2`: 서비스 기능 마비 또는 대규모 오남용
  - `SEV-3`: 영향 제한적, 즉시 차단 가능한 이슈

## 2) 즉시 차단 (Containment)

### 프론트/배포 측

- Vercel에서 최근 배포 상태 확인, 의심 배포는 즉시 롤백
- 필요 시 임시 점검 페이지로 전환해 쓰기 트래픽 차단

### Supabase 측

- 프로젝트 API 사용량 및 Auth/DB 로그 확인
- RLS 정책 점검:
  - `anon`에 과도한 `insert/update/delete` 권한이 없는지 확인
- 키 로테이션:
  - 노출/악용 의심 시 anon key 재발급 후 배포 환경변수 갱신

## 3) 근본 원인 수정 (Eradication)

- 취약 의존성: `npm audit fix` 또는 안전 버전으로 수동 업그레이드
- 코드 취약점: CodeQL/SAST 지적사항 수정
- 데이터 정책 문제: RLS/제약조건/권한 SQL 보강
- 재발 방지 테스트 추가:
  - lint/typecheck/build/security 워크플로우 통과 필수화

## 4) 복구 (Recovery)

- hotfix 배포
- `npm run check` 및 보안 워크플로우 수동 재실행
- Supabase 핵심 사용자 시나리오 회귀 확인
- 24시간 모니터링 강화

## 5) 사후 조치 (Postmortem)

- 타임라인 문서화(탐지 시각, 차단 시각, 복구 시각)
- 사용자 영향 범위 정리
- 액션 아이템 등록:
  - 탐지 자동화 보강
  - 권한 최소화 강화
  - 로그/알림 채널 보완

- [ ] Dependabot PR 주간 생성 확인
